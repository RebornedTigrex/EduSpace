# TIGREX Architecture README (Before Code) - v2
Этот документ фиксирует архитектурный контракт и "переводчик идей" перед реализацией.
Цель: убрать противоречия, сохранить скорость разработки и сделать решения повторяемыми для нейросетей и команды.
Если есть конфликт между разделами - всегда побеждает раздел `Architecture Contract (MUST)`.

## 1) Core принципы
- Core v1.0 не изменяется.
- Никакого хардкода путей и окружения: только относительные/гарантированные пути и конфиг.
- Модули небольшие, с одной зоной ответственности.
- Минимизировать связность между модулями и избегать "всё-в-одном" модулей.
- Горизонтальное взаимодействие сущностей одного уровня - через контракты и события.
- Аудиопередача только через SFU mediasoup WebRTC.

## 2) Architecture Contract (MUST)
### 2.1 Уровни абстракции (1/2/3/n+1)
- `L1` - низкоуровневая реализация: транспорт, системные примитивы, инфраструктурные драйверы, базовые шаблоны и утилиты.
- `L2` - сервисная логика: связывает несколько L1-компонентов, оперирует техническими доменными объектами.
- `L3` - фичевая/прикладная логика: управляет смысловыми сущностями, не знает деталей L1.
- `L(n+1)` - композиция абстракций уровня `Ln`; работает через контракты более низкого уровня.

Критерий уровня:
- чем ближе код к "сырым" данным и протоколам - тем ниже уровень;
- чем ближе код к пользовательскому смыслу и сценариям - тем выше уровень.

### 2.2 Вертикальная и горизонтальная связность
- Вертикаль (ось `Y`) - путь от инфраструктуры к бизнес-смыслу (`L1 -> L2 -> L3`).
- Горизонталь (ось `X`) - соседние сущности одного уровня, но разного смысла (например, текст и аудио на одном уровне).
- Правило: вертикальные зависимости только вниз по контрактам; горизонтальные взаимодействия - через eventbus/контракты без плотной прямой связки.

### 2.3 Направление зависимостей
Слои:
- `L1`: Infrastructure/Transport
- `L2`: Services/Adapters
- `L3`: Features/Application
- `L4`: App Composition (`main.cpp`, bootstrap, lifecycle wiring)

Допустимое направление: `L4 -> L3 -> L2 -> L1`.
Недопустимо: обратные зависимости и обход слоёв.

### 2.4 Action-first модель
- `Action` - атомарное типизированное намерение (`SendMessage`, `RebuildMemorySnapshot`, `GiveFile`).
- `Action` - основа feature-agent структуры.
- Любой action валидируется по DTO/схеме до выполнения.
- Action исполняется только агентом.

### 2.5 Agent
- Агент - исполнитель группы близких use-case в одной смысловой зоне.
- Агент не знает транспортный слой.
- Агент использует сервисы через интерфейсы.
- Прямые вызовы `Agent -> Agent` запрещены.
- Граница декомпозиции: если операции используют одни и те же инварианты/состояние, они остаются в одном агенте.

### 2.6 Feature
- Feature - модуль-агрегатор и "лицо" доменной области.
- Feature содержит агентов своей области и маршрутизацию к ним.
- Feature может иметь лёгкое координационное состояние, но основное состояние должно жить в сервисах ниже.

### 2.7 Command Router (обязательный сегмент)
Контракт команды:
`{ RouteObject, Agent, Action, Context }`

Где:
- `RouteObject` - target feature;
- `Agent` - агент внутри feature;
- `Action` - типизированное намерение;
- `Context` - типизированные данные вызова.

Правила:
- Router работает только с зарегистрированными feature/agent/action.
- Router не содержит бизнес-логики исполнения.
- Router выполняет резолв + валидацию + делегирование.

### 2.8 EventBus policy
- EventBus - для межмодульных/интеграционных событий.
- EventBus не заменяет явные бизнес-команды.
- Бизнес-исполнение: `command -> feature -> agent`.

### 2.9 Где использовать команды, а где события
Использовать `Command`, если:
- нужно изменить состояние системы или выполнить бизнес-операцию;
- нужен конкретный исполнитель (feature/agent) и детерминированный результат;
- важны строгая валидация контекста и предсказуемая обработка ошибок;
- операция должна быть явно трассируема по цепочке вызова.

Использовать `Event`, если:
- нужно уведомить другие модули о факте уже произошедшего действия;
- подписчиков может быть несколько (`0..N`) и их состав может меняться;
- реакция является побочной/интеграционной, а не первичным бизнес-действием.

Запрещено:
- запускать ключевые бизнес-сценарии только через eventbus без входной команды;
- публиковать event как замену обязательной валидации command-контракта;
- переносить ответственность исполнения из агента в подписчики событий.

## 3) Lifecycle как plugin-система (MUST)
Каждый участник lifecycle - плагин с единым контрактом:
- `pluginId`, `version`, `kind`
- `dependencies`
- `register(container, bus)`
- `init()`
- `start()`
- `stop()`

Правила:
- Загрузка и запуск строго детерминированы по графу зависимостей.
- Циклы зависимостей - ошибка запуска.
- Скрытая инициализация вне lifecycle запрещена.
- Любая feature подключается как plugin-участник lifecycle.

## 4) Bootstrap flow (App/main)
`main.cpp`:
- точка старта;
- парсинг аргументов;
- запуск app composition.

App composition порядок:
1. Инициализация базовых модулей (`eventBus`, `moduleRegistry`, config, logging).
2. Инициализация технических/сервисных модулей.
3. Инициализация features.
4. Инъекция агентов в features через регистрацию.
5. Регистрация команд feature/agent/action в command router.
6. Запуск lifecycle (`start`) по графу зависимостей.

## 5) Классификация модулей
- Технические (низкоуровневые): TCP, WebSocket, thread pool, DB-драйверы и инфраструктура.
- Сервисные (средний уровень): auth/session/routing/room management/repositories.
- Фичевые (верхний уровень): chat/calls/conference/file-sharing.

Критерий:
- если модуль знает протоколы/потоки/драйверы - это технический;
- если модуль связывает инфраструктуру и даёт прикладные операции - сервисный;
- если модуль реализует пользовательский сценарий - фичевый.

## 6) Где нужен orchestration слой
Orchestration слой вводится, если:
- сценарий затрагивает несколько агентов/фич;
- есть длинный flow с retry/timeout/compensation;
- нужна явная трассировка процесса.

Если сценарий локален внутри одной смысловой области - оставляем в агенте (+ middleware).

## 7) Developer workflow: добавление новой фичи
1. Создать `features/{feature}` с отдельными файлами feature.
2. Добавить действия в `features/{feature}/actions`.
3. Добавить агентов в `features/{feature}/agents`.
4. Зарегистрировать feature и агенты в lifecycle/plugin-реестре.
5. Зарегистрировать `RouteObject/Agent/Action` в command router.
6. Прогнать scenario gate и минимальные проверки.

## 8) Translator (пояснение языка абстракций)
Этот раздел объясняет авторский язык:
- Вертикаль (Y): степень удаления от "сырых" инфраструктурных деталей.
- Горизонталь (X): сущности одного ранга абстракции, но разного смысла.
- Feature - интерфейс смысловой области.
- Agent - исполнитель действий в области.
- Action - минимальная семантическая единица, из которой собираются сценарии.

Практический пример (идея ММСП):
- Модуль маршрутизации сообщений к пользователям работает с пользовательскими идентификаторами/псевдонимами.
- Он не оперирует деталями TCP.
- Нижний транспорт сопоставляет абстрактные адреса с фактической доставкой.
- Верхний модуль инициирует отправку через контракт, не "закапываясь" в сетевую реализацию.

## 9) Red Flags (признаки, что архитектура "плывёт")
- Появился god-agent/god-module.
- Feature, agent и service дублируют ответственность друг друга.
- Business flow полностью размазан по eventbus без явной последовательности.
- Router начинает выполнять бизнес-логику.
- Появились правила, противоречащие этому контракту.

## 10) Controlled Experiments (без развала архитектуры)
Режимы:
- `Stable`: текущий контракт и поставка.
- `Lab`: гипотезы и эксперименты.

Ограничения:
- 1 эксперимент = 1 гипотеза.
- У каждого эксперимента есть критерий успеха, срок и условие отката.
- Без измеримого выигрыша эксперимент не переносится в Stable.
- Крупный архитектурный эксперимент и критичную поставку нельзя смешивать в одном изменении.

## 11) Mini ADR (обязателен для спорных решений)
На каждое архитектурное изменение:
1. Проблема.
2. Решение.
3. Что отклонено.
4. Какие правила затронуты.
5. Какие сценарии перепроверены.

## 12) Scenario Gate (проверка любого изменения)
Любое архитектурное изменение обязано пройти:
1. 1:1 чат (сообщение туда-обратно).
2. Конференция: голос + экран + переписка.
3. Нагрузка на одну страницу: 10 человек одновременно.
4. 2 человека загружают файлы + 3 одновременно выполняют тяжёлые действия в веб-интерфейсе.
5. Добавление новой фичи без изменения Core v1.0.

Если хотя бы в одном сценарии нужны "особые исключения", решение не готово для Stable.

## 13) Before Code Checklist
Перед началом реализации:
- Ясно, какой action добавляется/меняется.
- Понятно, какой агент за него отвечает.
- Определён target feature и путь через router.
- Нет нарушения направленности зависимостей.
- Нет обхода lifecycle/plugin-регистрации.
- Изменение прошло Scenario Gate.

Если любой пункт "нет" - сначала доуточнить контракт, потом писать код.
